## 零之二、第二轮修复（2026-09-16 晚）：个人中心 + 后端「用户阅读数据」页

**起因**：用户反馈「安卓前端和 web 前端阅读书籍和修改个人信息后，后端无数据」。

**排查结论（代码走查 + 线上 `8.148.8.146:8080` 实测）**：阅读数据其实**写进去了**，问题出在两处——

1. **后端（真缺陷）**：管理后台「用户阅读数据」页 (`templates/admin/user-reading.html`) 直接 `fetch /api/user/bookshelf/{id}`、`/api/user/progress/recent/{id}`、`/api/user/bookmark/{id}/{bookId}`。这三个接口在 `UserDataController` 里有 `checkOwner()` 归属校验，而管理员浏览器只带 `ADMIN_TOKEN` Cookie（JWT 主体＝**管理员自己**的主键），于是查任何他人一律 `403 无权访问他人数据` → 前端拿不到 `data` → 页面永远渲染「暂无数据」。
   实测：管理员(19) 查用户 13/11 → `{"code":403,"message":"无权访问他人数据"}`；查自己(19) → 200。
2. **App 端**：`ProfileActivity.saveProfile()` 只写本地 `SharedPreferences("user_info")`（昵称/性别/头像），**全仓 `ApiService` 没有任何用户资料更新接口** → 后端 `users` 表必然不变。
3. **Web 端**：**根本没有个人中心/资料编辑入口**（`navItems` 只有 首页/书城/书架/发现，用户菜单只有「我的书架」「退出登录」）。

## 零之三、第三轮修复（2026-09-16 晚）：web 端「阅读后没有阅读记录」

**起因**：用户反馈「web 端阅读后没有阅读记录」。

**排查方式**：先用管理后台只读接口 `GET /api/admin/users/{id}/reading` 批量看线上**所有真实账号**的阅读数据（这一步直接定死了方向），再用无头 Edge 完整复现「登录 → 打开阅读器 → 翻章 → 滚动 → 点导航离开 → 回首页 / 书架页」。

**决定性证据**：真实账号 `u18253956807`(id=49) 在 **20:16**（报障前 1 分钟）读过《修仙就是这样子的》，服务端该条记录 `chapterIndex = null`；而他 **18:45** 读《诸天尽头》的记录 `chapterIndex = 7` 正常。同一账号、同一天，web 端写入的是 `null`。

**三个根因（全部在 `web/index.html`，纯前端）**

| # | 根因 | 后果 |
|---|---|---|
| 1 | **保存时用了失效的路由参数**：`saveProgress()` 直接读 `chapterIndex.value`，而它是 `route.params.chapterId` 派生。离开阅读器时路由已切走 → `Number(undefined) - 1 = NaN` → `Math.max(0, NaN) = NaN` → JSON 序列化成 `null` | 后端 `updateProgress` 是**无条件** `SET r.chapterIndex = :chapterIndex`，`null` 直接落库，**把真实的阅读位置覆盖掉**。下次「继续阅读」回到第 1 章 |
| 2 | **「最近阅读」用百分比判断有没有读过**：`progress > 0` 过滤，而百分比是 `Math.round((idx+1)/chapterCount*100)`，只读了开头几章（如 3/1305）四舍五入就是 **0** | 明明有阅读记录，却被当成「没读过」过滤掉 → 首页「最近在追」显示「书架里还没有开始阅读的书」、书架页「最近阅读」标签空白 |
| 3 | **首页从不加载书架数据**：`store.shelf` 只在书架页 / 登录时拉取，首页 `onMounted` 只拉 hot/latest/recent | 直接打开首页时，「最近在追」和「书架 N 本 · 在读 M 本」永远是空的；且 `saveProgress()` 只刷新 `store.recent`，不通知书架缓存失效，读完书回首页仍是旧数据 |

**修复内容（归属：前端 `web/index.html`）**

| 项 | 修复内容 |
|---|---|
| 位置快照 | 新增 `savedPosition{chapterIndex, scrollPosition}` + `syncPosition(params.chapterId)`：只在路由确实停在某个章节时才更新快照，离开后保留最后有效值。`queueSave()` / `saveProgress()` 一律读快照，不再碰失效的 computed |
| 离开时保存 | 用 `onBeforeRouteLeave(to, from)` 取代原先 `onUnmounted` 里的保存——守卫触发时路由尚未切换，`from.params.chapterId` 是真实章节号 |
| 补 chapterId | 保存时带上 `chapterId`。后端该列同样是无条件覆盖，不带就把之前的章节信息冲成 `null`，后台「用户阅读数据」看不到「读到哪一章」 |
| 滚动即保存 | 加 `scroll` 监听（passive + 800ms 防抖），只在一章内滚动也能记录位置 |
| 过滤条件 | 首页「最近在追」与书架「最近阅读」标签的判断由 `progress > 0` 改为 `chapterIndex >= 0`（有阅读记录即算在读） |
| 首页补书架 | 首页 `onMounted` 补 `loadShelf()`；`saveProgress()` 成功后置 `store.shelfLoaded = false`，让首页/书架页下次进入时重新拉取 |

**回归验证证据（无头 Edge + 线上后端 `8.148.8.146:8080`，测试数据跑完已清理）**

## 零之四、第四轮（2026-09-16 晚）：web 与 App 共用同一条进度记录的对齐

**需求**：一本书只保留一条进度记录，按「最后阅读时间」取最新的一条；两端同时在线时以最后一次阅读退出为准。粒度上：App 同步 web 的记录只需对应到章节，web 消费 App 的记录也只需章节，App↔App 才需要精确到页；不做客户端类型标记，只把 web 保存的「页」数据固定成当前章节首页，web 同步时不使用页数据。

### 根因（两侧各一处）

| # | 根因 | 归属 |
|---|---|---|
| 1 | `saveProgress()` 上报的是 `window.scrollY`（**像素偏移**），而 App 的 `scrollPosition` 是**章节内页码（1 基）** —— 同一个字段两种语义。web 写 600 像素，App 读成「第 600 页」（越界后回落到第 1 页，位置信息全丢） | **前端（web）** |
| 2 | App 只在「本地没有该书阅读记录」时才拉服务端进度（`!hasLocalRecord(bookId)`），且入口章节非 0 时完全不拉 —— 一旦在安卓上读过，**web 端写入的新位置在 App 上永远看不到** | **前端（App）** |

### 改动清单

| 项 | 归属 | 改动 |
|---|---|---|
| 1 | 前端(web) | `PROGRESS_CHAPTER_FIRST_PAGE = 1`：进度里的「页」固定上报 **1**（= 该章首页）。App 的 `reader.html` 用 `currentPage = scrollPosition - 1`，所以 App 读到 web 记录时正好落在该章第一页 —— 无需任何客户端类型标记 |
| 2 | 前端(web) | 位置快照只记章节（去掉 `window.scrollY` 像素追踪）；**打开书本身不写记录**，只在「换章 / 滚动 / 点击 / 滚轮 / 键盘 / 离开页面(`pagehide`·`visibilitychange`)」后写 —— 避免打开看一眼就把另一端刚写入的位置顶掉 |
| 3 | 前端(App) | `fetchServerProgress` 改为**总是**拉取（去掉 `!hasLocalRecord` 与 `targetChapter == 0` 限制），并按**最后阅读时间**取舍：`服务端 updatedAt` 比本地 `record_readTime_` 新才采纳，否则保留本地（离线读的本地可能更新） |
| 4 | 前端(App) | 新增 `adoptServerPosition()`：正文已在手上就直接按服务端页码重渲染（用 `forceRestorePosition` 越过 `positionRestored` 守卫）；换了章 / 正文没到就走既有「在途跳转」通道（`pendingChapterPage`），正文到位后按页码渲染。服务端页码原样使用：web 记录 → 该章首页，App 记录 → 精确页码 |
| 5 | 前端(App) | `bean/ReadingProgress` 补 `updatedAt`（String）+ `parseServerUpdatedAt()` 解析服务端 ISO 时间 |

### 回归验证证据

**web 端（无头 Edge + 线上后端，测试记录用后即删）**

| 用例 | 结果 |
|---|---|

## 零之六、第六轮修复（2026-09-16 晚）：三条遗留一次修完（**后端 + App + web**）

### ① `updatedAt` 无时区 → 改下发 `updatedAtEpoch`

## 二、P0 级问题（必现、影响核心链路）

### P0-1 跨域预检被 Spring Security 拦截 → 登录后所有接口失败（归属：**后端**）

**实测证据（无头 Edge，页面从 `http://localhost:5597` 发起跨域请求）**

```
A GET  /api/books            无自定义头        -> status=200      ✅ 通过
B GET  /api/books            带 Content-Type   -> Failed to fetch ❌ 被拦
C GET  /api/bookshelf/user/1 带 Authorization  -> Failed to fetch ❌ 被拦
D POST /api/auth/login       带 Content-Type   -> status=200      ✅ 通过
G GET  /api/books            带 Authorization  -> Failed to fetch ❌ 被拦
H GET  /api/chapters/book/727 带 Authorization -> Failed to fetch ❌ 被拦
```

curl 直接探测预检请求，可见根因：

```
$ curl -X OPTIONS http://8.148.8.146:8080/api/books \
       -H "Origin: http://localhost:5500" \
       -H "Access-Control-Request-Method: GET" \
       -H "Access-Control-Request-Headers: content-type"

HTTP/1.1 401                      ← 预检就 401 了
（响应头里没有 Access-Control-Allow-Origin）
{"code":500,"success":false,"message":"用户未登录，请先登录","data":null}
```

**根因**：`SecurityConfig` 里**没有启用 `.cors()`**，`@CrossOrigin(origins="*")` 只作用于 Spring MVC 层；而 Spring Security 过滤器链跑在 `DispatcherServlet` **之前**，OPTIONS 预检请求不在 `permitAll` 的 GET 白名单里，于是落到 `anyRequest().authenticated()` → 401。浏览器拿不到 `Access-Control-Allow-Origin`，直接判失败。

`/api/auth/**` 因为对**所有方法** `permitAll`，所以预检能过 —— 这也解释了为什么"登录能成功，但登录之后什么都加载不出来"。

**影响链路**
- `api` 的请求拦截器只要 `localStorage` 里有 token，就会给**每一个**请求加 `Authorization` → **登录后所有请求都触发预检 → 全部失败**。
- 失败 → `loadAllBooks` / `loadShelfBooks` / `loadReader` 的 `catch` 静默回落 mock。用户看到的是**假书籍、假书架**，没有任何提示。

**修复方向**（后端，二选一）
1. `SecurityConfig` 补 `.cors(Customizer.withDefaults())` + 暴露一个 `CorsConfigurationSource` Bean（`allowedOriginPatterns("*")`、`allowedHeaders("*")`、`allowedMethods("*")`），并把它放在授权规则最前面；
2. 或在 `authorizeHttpRequests` 里显式放行预检：`.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()`（1 是根治，2 是兜底）。

> 备注：若把 `web/` 作为静态资源**同源部署**进后端 `static/`，跨域问题自然消失；但当前 `web/` 是独立目录、且用 `localStorage.apiBaseUrl` 指向远端，属跨域用法，必坏。

### P0-2 所有书籍评分恒为 `0.0`、评价数恒为 `0`（归属：前端字段映射错 / 后端缺字段）

`index.html` 里：

rating: formatRating(raw),

| 书架 Tab | 最近阅读 / 已读完 / 想读 —— `activeTab` 不参与任何筛选 |
| 首页「继续阅读」 | 按钮无 `@click` |
| 详情页「分享」 | 按钮无 `@click` |
| 书架「+ 书城选书」 | 按钮无 `@click` |
| 登录页「忘记密码？」 | `href="#"`，无逻辑 |
| 讨论区 | 帖子/评论/点赞/热门话题**全是硬编码常量**，后端也没有对应接口 |
| 首页「晚上好」「连续阅读第 12 天」 | 写死，不随时间和数据变化 |

### P1-4 错误处理形同虚设 → 后端挂了也"看起来正常"（归属：前端）
```js
async function loadAllBooks() {
  try { ... } catch (e) { console.warn('书籍列表加载失败，使用 mock 数据:', e.message); }  // 吞掉异常
}
```
`loadAllBooks` 内部已 try/catch，**永不向外抛** → `Bookstore` 里的 `error` 永远赋不上值 → `v-else-if="error"` 分支是死代码。用户侧表现为："看起来一切正常"，实际全是 mock。

### P1-5 登录成功后书架不会重新加载（归属：前端）
`loadShelfBooks()` 只在根组件 `onMounted` 跑一次，且开头有 `if (!auth.isLoggedIn.value || !auth.user.value?.id) return;`。
登录成功后只 `router.push('/')`，**不会重新拉书架** → 书架、首页「最近在追」长期显示 mock 数据（《百年孤独》34% 等）。

### P1-6 注册流程与后端规则不匹配（归属：前端）
- 前端 label 是「用户名 / 邮箱」，注册时**没有做任何前端校验**；
- 但 `POST /api/auth/register` 只接受 `username`，且后端规则为 `^[A-Za-z][A-Za-z0-9_]{2,19}$`；
- → 用户填邮箱（含 `@`）或中文名会被后端拒绝，报错信息直接抛给用户；
- 后端已实现邮箱注册（`/api/auth/email-code` + `/api/auth/register-by-email`）和验证码登录（`/api/auth/login-by-code`），**前端一个都没接**，也没有「验证码登录」Tab。

### P1-7 无 404 路由（归属：前端）
`createRouter` 只注册了 7 条路由，没有 catch-all。访问任意未知路径（如 `#/xxx`）→ `#app` 内容区**空白**，没有任何提示。

### P1-8 401 不自动登出（归属：前端）
响应拦截器把错误包成 `{message, status}` 就 reject 了，没有对 `status === 401` 做统一处理。token 过期后：请求全部失败，但 `localStorage.token` 仍在 → 顶栏头像还在、`isLoggedIn` 仍为 `true`，用户卡在"假登录"状态。

## 五、没有问题的部分（已实测通过）

- 匿名打开页面可正常渲染，能拉到线上真实数据（首页书城推荐显示《苟在初圣魔门当人材》等真实书名）；
- 匿名阅读链路可用：`#/read/727/1` 成功渲染真实章节标题「第一章 开局师父没了」；
- 登录 / 注册接口路径与后端一致（`POST /api/auth/login`、`POST /api/auth/register` 均存在），`LoginResponse` 的 `id` / `userId` / `token` 字段与前端读取方式对得上；
- `/api/bookshelf/add`、`/api/bookshelf/user/{userId}` 路径存在，且后端已改为**从 JWT 派生 userId、忽略路径 id**，前端传 `auth.user.id` 不会有越权问题；
- `adaptBook` 对 `title / author / category / intro / wordCount / status / chapterCount` 的映射与实际响应字段一致（`status===1`→完结，与后端语义相符）；
- 分页结构按 `data.content` 读取，与 Spring Data `Page<T>` 格式一致。
